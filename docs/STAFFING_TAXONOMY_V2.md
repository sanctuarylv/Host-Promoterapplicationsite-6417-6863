## 1. Architecture

Three layers, deliberately separate:

```
master taxonomy (36 canonical roles)  ─▶  staffing template (After Dark v1; vNext preview)  ─▶  event plan (per event)
   ops_canonical_roles                      ops_templates / ops_template_versions /            ops_events /
   (new, migration 0002)                    ops_template_roles (existing)                      ops_event_role_overrides
                                                                                                └▶ ops_assignments (people)
```

- **Master taxonomy**: what roles exist in the paid Sanctuary LV Group, with identity, department,
  reporting line, headcount model, seniority, applicability, credential and training text.
  It is never an event plan and never creates assignments.
- **Staffing template**: a versioned selection of roles and counts for a type of event. After Dark v1 stays
  the published, active template. The vNext proposal derived from the taxonomy is **preview-only**
  (§9).
- **Event plan**: per-event counts (`ops_event_role_overrides`) and assignments of real people. The
  taxonomy does not touch it.

## 2. Canonical IDs and entity boundary

- Each role has a stable **canonical ID** `SLVG-EVT-001` … `SLVG-EVT-036` (`^SLVG-EVT-\d{3}$`). It is the primary
  key of `ops_canonical_roles` and the upsert key of the importer. Display names may change; IDs do not.
- Exactly **36** unique IDs are required. Fewer, more, duplicates, malformed IDs, or IDs that are not in the
  reviewed map are validation errors (`role_count`, `duplicate_id`, `bad_id`, `unmapped_id`).
- **Entity:** every row must be `sanctuary_lv_group`. `sanctuary_lv` (the nonprofit) is rejected as
  `nonprofit_conversion`; any other entity is `unknown_entity`.
- **Opportunity type:** must be `paid` (`invalid_opportunity` otherwise).
- **Classification:** `engagement_type` must be `pending_classification`. The importer never infers
  employee / contractor status; any other value is `invalid_engagement`. Worker classification is out of
  scope for this phase.
- The nonprofit Serve Team (`serve_coordinator`) and venue/provider roles can never become Group roles:
  mapping one of them is an error (`nonprofit_conversion`, `external_conversion`).

## 3. Role-key compatibility

`role_key` is the internal key used by templates, assignments, campaign goals and public apply options.

- Where a canonical role continues an existing After Dark v1 seat (exact / rename / partial), the
  **existing key is kept** (`legacy_key_not_preserved` is an error). Example: SLVG-EVT-005 is displayed
  "Guest Experience Manager" but keeps `guest_experience_lead`, because that key is a public apply option
  and a campaign goal.
- New roles get a new snake_case key derived from the canonical name and fixed in the map.
- `role_key` is unique in `ops_canonical_roles` (`ops_canonical_roles_role_key_uq`). A target row that holds
  the key under a different ID is a `target_conflict` error, never an overwrite.
- The previous title is kept as `legacy_display_name` and in `aliases`, so search and reports still find
  "Operations Lead", "Door Team", etc. No fuzzy matching is used anywhere; the map is the only source of
  identity decisions.

## 7. Credentials

The only access model in the repository is the zone list on template roles, copied to assignments and to issued
credentials (`ops_template_roles.zones → ops_assignments.zones → ops_credentials.zones`). The existing zones are
`front_of_house`, `back_of_house`, `stage`, `vip`, `all_staff`. No parallel credential system is introduced and
no zone is invented.

`credential_level` text is split on `/` and each token goes through a reviewed table (`credentials.ts`):

- zone tokens (`FOH`, `Floor`, `Backstage`, `Green Room`, `Loading`, `Facilities`, `VIP`, `All Access`,
  `Production`) → existing zones;
- descriptor tokens (e.g. "Executive Credential") are recognised but grant nothing;
- conditional wording ("as required", "as approved", "as applicable") is never auto-granted;
- anything else is **unknown** → warning `credential_gap`, grants nothing.

Result: **mapped 27 · partial 1 · unresolved 8** (unresolved = no zone could be proposed: `venue_liaison`,
`accessibility_guest_care_host`, `community_outreach_street_team_lead`, `community_outreach_street_team`,
`security_manager_venue_security_liaison`, `access_control_credential_lead`,
`safety_incident_response_coordinator`, `event_admin_staff_check_in_coordinator`; partial: `vip_host`).
11 `credential_gap` warnings across 9 roles. The raw text is stored; the proposed zones are shown in the plan only.
Nothing writes a template role, assignment, credential or permission.

## 9. Templates — After Dark vNext (preview only)

After Dark **v1 stays the published, active template, unchanged**. `vnext.ts` computes "After Dark — Proposed
Staffing Template vNext" as a diff against v1. It never writes a template version, never activates anything,
never replaces v1.

Rules (reviewed assumptions):

1. A canonical role continuing an existing v1 seat stays **enabled**; its proposed count is the canonical baseline.
2. A **new** required / recommended / scalable role is enabled only when its `event_applicability` is in the
   After Dark applicability profile (`AFTER_DARK_APPLICABILITY`: All Events, Public Events, Programmed Events,
   Venue-Based Events, Ticketed/Registered Events, Growth Events, Music/Programmed Events, Credentialed Events,
   Load-In Events).
3. A **new event_specific** role is **off by default**, whatever its applicability.
4. Every v1 role the workbook does not cover (19) is **carried forward unchanged** with its disposition. Nothing
   is removed.

Result: new 10 · changed 16 · unchanged 1 · carried_forward 19 · not_enabled 9 · removed 0.
Sanctuary-side seats 51 (v1) → 72 (vNext: 51 Group seats + 21 carried-forward Sanctuary seats); 15 baseline
seats sit in not-enabled roles; 7 venue allowances unchanged.

Not enabled: `seating_floor_lead`, `seating_floor_host`, `community_outreach_street_team_lead`,
`community_outreach_street_team`, `monitor_stage_audio_engineer`, `livestream_broadcast_producer`,
`talent_artist_relations_manager`, `backstage_green_room_coordinator`, `cashless_pos_merch_lead`.

Migration 0002 adds the columns a future reviewed template version will need (`ops_template_roles.canonical_role_id`,
`enabled` default true, `required` default false; `ops_templates.entity_id`, `updated_at`). They are additive and
nullable/defaulted; existing rows and the seed are unchanged (verified by seeding baseline and new code into fresh
DBs and diffing).

## 10. Event plans

Event plans (`ops_events`, `ops_event_role_overrides`, `ops_assignments`) are untouched by the taxonomy, the
importer and the preview. `event_applicability` is planning metadata: it never schedules a role onto an event.
Historical assignments remain exactly as they are (migration rehearsal: assignment and training-record counts
identical before and after apply).

## 11. Public application distinction

Public apply roles stay **curated** (`crew/contract.ts` `ROLE_OPTIONS`: host, promoter, both, not_sure,
guest_experience_lead, promoter_manager). The taxonomy never adds an option (`exposed_by_taxonomy: []`).

The one public option whose canonical title changed — `guest_experience_lead`, "Guest Experience Lead" →
"Guest Experience Manager" — is a **prepared** display rename (`PUBLIC_ROLE_RENAMES`, `prepared_not_applied`).
The key stays the same, so existing applications, campaign goals and scorecards are unaffected when the label is
eventually changed.
